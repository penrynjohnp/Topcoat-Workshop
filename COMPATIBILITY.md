CLI 0.7.0: no top-level `--version`, and `topcoat fmt` has no `--check` (CI formats then `git diff --exit-code`). Attribute render order is not guaranteed once an element takes a spread `Attributes`, so lab tests assert on the attribute set. Runtime expressions have no `&&`/`||` and no `match`; Lab 07 spells combinations with `if`/`else`. The runtime script is an asset, so Lab 07's router takes an `Option<AssetBundle>` and tests pass `None`. Lab 08 explicitly calls `discover_shards()` and `discover_procedures()`; shard arguments are JSON tuples (for one `String`, `["Lady"]`), and streamed swaps arrive in the original response as template/script envelopes. `topcoat::htmx` sits behind the non-default `htmx` feature, so Lab 09 enables it per-crate (`topcoat = { workspace = true, features = ["htmx"] }`) rather than in `[workspace.dependencies]`; this pulls in `topcoat-htmx` 0.7.0. htmx itself is pinned to `htmx.org@2.0.10` from jsDelivr in the Lab 09 layout (Lab 11 vendors it with `asset!`). `view!` rejects bare boolean attributes, so the script tag needs `defer="defer"`. htmx response responders implement `IntoResponseParts` and must precede the body in the response tuple; a `view!` fragment becomes a body with `.single().await?`. Toasty 0.10.0 `push_schema()` is used only for a new Lab 10 SQLite file because a repeated push is not idempotent; operations take `&mut Db`, relationship queries use generated accessors, and Topcoat runtime numeric procedure arguments arrive as `f64` before conversion to Toasty's `u64` key. Lab 11 enables `tailwind`, `font-fontsource`, `icon-iconify`, and `ui`; the build script uses the standalone Tailwind CLI pinned by Topcoat to 4.3.2 and stages Lucide. Self-hosted Fontsource expands through a direct `topcoat-asset` dependency. CLI 0.7.0 has no `topcoat build`; use Cargo and `topcoat asset bundle` with matching profiles. Release assets are written beside the binary in `target/release/assets/`. Lab 12 adds `azure_core` 0.30.1 (`default-features = false`; `reqwest`, `reqwest_gzip`, `tokio`) and `azure_identity` 0.30.0 (`default-features = false`; `tokio`) for the `ManagedIdentityCredential` token fetch, plus `base64` 0.22, `percent-encoding` 2.3, `tracing` 0.1, and `tracing-subscriber` 0.3 (`env-filter` + `json` features). Its Dockerfile builds and bundles in one BuildKit stage using `--mount=type=cache` on the Cargo registry and `target/` rather than the classic empty-`main.rs` dependency-caching trick, so no stale-shim source file ever ships. Toasty 0.10.0's non-idempotent `push_schema()` requires Lab 12's PostgreSQL connector to probe `to_regclass('public.berths')` and bootstrap only a fresh database, so normal restarts do not recreate existing tables; this is not a migration system. **Toasty 0.10.0's PostgreSQL driver has no renewable-token callback**: `connect_managed_postgres` in `src/production.rs` fetches one Entra access token and hands it to `toasty::Db::builder().connect(...)` as a static, percent-encoded password, so a pool connection opened after that token expires can fail to authenticate until the process restarts. This managed-identity PostgreSQL path is therefore **experimental**, workshop- and demo-appropriate, not a production connection-pooling story until Toasty adds a refresh callback. Watch for that capability before relying on this beyond Lab 12. Lab 12 provisions **two** user-assigned managed identities: `infra/modules/identity.bicep` is a single reusable factory module that `main.bicep` instantiates twice — once for the app (ACR pull, Key Vault Secrets User, PostgreSQL Entra administrator) and once for a narrowly-scoped bootstrap identity (Key Vault Secrets Officer only, never attached to the container app, never granted ACR pull or database access). The cookie signing key secret is created by `infra/modules/secret-bootstrap.bicep`, an idempotent `Microsoft.Resources/deploymentScripts` (`kind: 'AzureCLI'`) resource running under the bootstrap identity; `main.bicep`'s `app` module declares `dependsOn: [secretBootstrap]` because Azure Container Apps validates `keyVaultUrl` secret references at deploy time and fails the whole deployment if the target secret doesn't exist yet — a postprovision hook, which only runs after the app module is already submitted, is too late to create it. Consequently `scripts/azd-postprovision.sh` never creates or reads a secret value; it is read-only control-plane verification that the deployed container app is attached to its own user-assigned identity and that its Key Vault secret reference resolves through that same identity. Lab 12's `postgres.bicep` registers the *app's* identity (not the bootstrap identity) as the PostgreSQL Entra *administrator* — a bootstrap shortcut that keeps the lab to one extra Bicep module rather than a third identity, not a least-privilege pattern for production, where the administrator role belongs to a human or break-glass identity and the app gets a narrower Entra role. Azure Files was deliberately not used to keep SQLite in Lab 12: Container Apps' Azure Files integration authenticates the mount with a storage account key, not a managed identity, which would have reintroduced exactly the stored-secret pattern the "managed identity everywhere" rule forbids — PostgreSQL with Entra-only auth (`activeDirectoryAuth: 'Enabled'`, `passwordAuth: 'Disabled'`) replaces it instead. |topcoat-icon cache write is not atomic; CI stages one crate first

## Upgrading

1. Bump versions in the workspace `Cargo.toml` (`[workspace.dependencies]`) and `scripts/setup.sh`.
2. `cargo build --workspace && cargo test --workspace`.
3. Fix breakages lab by lab; each fix PR adds a row here.
